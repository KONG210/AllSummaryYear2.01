## 1. Quality Assurance vs Quality Control

| | Quality Assurance (QA) | Quality Control (QC) |
|---|---|---|
| นิยาม | **ทุกกิจกรรม** ที่ออกแบบมาเพื่อ **วัดและปรับปรุงคุณภาพ** ของ **ผลิตภัณฑ์และกระบวนการ** | กิจกรรมที่ออกแบบมาเพื่อ **ยืนยันคุณภาพของผลิตภัณฑ์และหา fault** |
| เน้น | process + product | product |

ทั้งสองต้องมี **process, tools และทีมที่ดี**

> ⭐ QA กว้างกว่า (ป้องกัน, ปรับกระบวนการ) · QC แคบกว่า (ตรวจผลงาน, หาข้อผิดพลาด)

## 2. Error Detection Techniques (6 แบบ)

### 🔹 1) Code Review
ตรวจ source code หา defect **ก่อนรัน**
- **Code inspection:** ตรวจอย่างเป็นระบบตามเกณฑ์ที่กำหนด
- **Peer review:** นักพัฒนาอีกคนตรวจ
- **Walkthrough:** **ผู้เขียนอธิบายโค้ดทีละขั้น** ให้ reviewer ฟัง
- **Static analysis:** tool อัตโนมัติวิเคราะห์โค้ด **โดยไม่รัน**

### 🔹 2) Testing
**รันซอฟต์แวร์** แล้วดูว่าพฤติกรรมตรงกับที่คาดไหม
- **Unit testing:** ทดสอบ function/class เดี่ยว
- **Integration testing:** ทดสอบการทำงานร่วมกันของ component
- **System testing:** ทดสอบทั้งระบบ
- **Acceptance testing:** ยืนยันว่าระบบตรง requirement ของผู้ใช้/ธุรกิจ
- **Regression testing:** ทำให้แน่ใจว่าการเปลี่ยนแปลงใหม่ **ไม่ทำให้เกิด defect ใหม่**

### 🔹 3) Static Analysis
หาปัญหา **โดยไม่รันโปรแกรม** เช่น syntax/type errors · **unused variables** · **unreachable code** · code smells · security vulnerabilities · potential null-pointer errors · ละเมิด coding standard

### 🔹 4) Dynamic Analysis
หาปัญหา **ขณะโปรแกรมรัน** เช่น runtime error detection · **memory leak detection** · performance monitoring · debugging · **code coverage analysis** · profiling

### 🔹 5) Debugging
หาตำแหน่งและสาเหตุของ failure **หลังจากพบ error แล้ว**
1. **Identify failure** → 2. **Reproduce the problem** → 3. **Locate the cause** → 4. **Fix the defect** → 5. **Test again**

**เทคนิค:** breakpoints · step-by-step execution · variable inspection · logging/tracing · stack-trace analysis

### 🔹 6) Formal Methods
ใช้ **เทคนิคทางคณิตศาสตร์** พิสูจน์ว่าซอฟต์แวร์มีคุณสมบัติตามที่กำหนด เช่น formal specification · **model checking** · **theorem proving** · formal verification

| | Static analysis | Dynamic analysis |
|---|---|---|
| รันโปรแกรมไหม | **ไม่รัน** | **รัน** |
| หาอะไรได้ | syntax, unused var, unreachable code, null pointer ที่อาจเกิด | runtime error, memory leak, performance, coverage |

## 3. What is "Quality"?
- **Conforms to requirements** (ตรงตาม requirement)
- **Fit to use** (เหมาะกับการใช้งาน)

## 4. Verification vs Validation (Ammann & Offutt)

| | Verification | Validation |
|---|---|---|
| นิยาม | กระบวนการตรวจว่า **ผลผลิตของแต่ละ phase** ตรงตาม requirement ที่กำหนดใน **phase ก่อนหน้า** | กระบวนการประเมินซอฟต์แวร์ **ตอนจบการพัฒนา** ว่าตรงกับ **การใช้งานที่ตั้งใจ** |
| คำถาม | **"Are we building the software right?"** | **"Are we building the right software?"** |

> ⭐ จำง่าย ๆ: Verification = ทำ **ถูกวิธี** (ตามสเปก) · Validation = ทำ **ถูกของ** (ตรงความต้องการจริง)

(สไลด์แสดงแผนภาพกิจกรรม V&V จาก Naik & Tripathy — เป็นรูป)

## 5. Software Faults, Errors & Failures

| คำ | นิยาม |
|---|---|
| **Fault** | **ข้อบกพร่องแบบ static** ในซอฟต์แวร์ (อยู่ในโค้ด) |
| **Error** | **สถานะภายในที่ผิด** อันเป็นผลจาก fault |
| **Failure** | **พฤติกรรมภายนอกที่ผิด** เทียบกับ requirement หรือพฤติกรรมที่คาดหวัง |

- fault ในซอฟต์แวร์ = **design mistake ในฮาร์ดแวร์**
- **ซอฟต์แวร์ไม่เสื่อมสภาพ (does not degrade)**

**ตัวอย่าง:** โค้ดเขียน `for (i = 1; i < n; i++)` แทน `i = 0` (**fault**) → ตอนรัน ตัวแปร sum ไม่รวมสมาชิกตัวแรก (**error**: สถานะภายในผิด) → โปรแกรมแสดงผลรวมผิดให้ผู้ใช้ (**failure**)

## 6. Testing
- กิจกรรมเพื่อ **ประเมินคุณภาพผลิตภัณฑ์** และ **ปรับปรุงโดยหา defect ให้แก้ก่อนปล่อย**
- **Dynamic verification** (รันโปรแกรม) ของพฤติกรรม บน **ชุด test case จำกัด** ที่เลือกจาก execution domain
- **Testing พิสูจน์ไม่ได้ว่าผลิตภัณฑ์ทำงาน 100%** — แม้ใช้แสดงว่าบางส่วนทำงานได้

### 🔹 Progression of Testing
**Unit Test → Component Test → Functional Test → System / Regression Test** (unit หลาย ๆ ตัวรวมเป็น component, component รวมเป็นระบบ)

### 🔹 Testing Techniques (มิติต่าง ๆ)
| Who tests | What is tested | Why test | How (test cases) |
|---|---|---|---|
| Programmers | Unit testing | Acceptance | Intuition |
| Testers | Functional testing | Conformance | **Specification based (black-box)** |
| Users | Integration / system testing | Configuration | **Code based (white-box)** |
| | User interface testing | Performance, stress | Existing cases (**regression**) |
| | | Faults | |

## 7. Black-box Testing

- เรียกอีกชื่อ **behavioral หรือ functional testing**
- เน้น **functional requirements**
- สร้างชุด **input conditions** มาทดสอบ function
- ทดสอบที่ **software interface** (ไม่ดูโค้ดข้างใน)
- **หา error ประเภท:** function ผิด/ขาด · interface errors · data structure หรือ external database access errors · behavior หรือ performance errors · initialization และ termination errors

เทคนิค: **Equivalence Class Partitioning (ECP)** และ **Boundary Value Analysis (BVA)**

### 🔹 Equivalence Class Partitioning (ECP)
- เทคนิค **specification-based, black-box**
- **แบ่ง input เป็นหลาย class** ที่ถือว่า "เทียบเท่า" กันในการหา error
- ใช้ **ตัวแทน 1 ค่าต่อ class** ในการทดสอบ
- กำหนด class จาก **สัญชาตญาณและ spec**
- หลักคิด: **"ถ้าโปรแกรม fail กับสมาชิกหนึ่งของ class ก็คาดว่าจะ fail กับสมาชิกอื่นทั้งหมด และกลับกัน"**

**ตัวอย่าง: หาค่าที่มากกว่า**
| Class | Representative |
|---|---|
| First > Second | 10, 7 |
| Second > First | 8, 12 |
| First = Second | 6, 6 |

**ตัวอย่าง: Age 18–56**
- Valid class: 18–56 (เลือก 1 ค่า เช่น 30)
- Invalid class 1: ≤ 17 (เช่น 10)
- Invalid class 2: ≥ 57 (เช่น 70)

**Exercise 1:** รับ 1–1000 → Invalid **≤ 0** · Valid **1–1000** · Invalid **≥ 1001**

**Exercise 2:** รับเฉพาะ 75, 253, 414 → Valid **75, 253, 414** · Invalid **ค่าอื่นทั้งหมด**

**Exercise 3: ค่าตั๋วอุทยาน**
- เด็กอายุต่ำกว่า 12: ฟรี · ผู้ใหญ่ 18–60: 200 บาท · ต่ำกว่า 18 และมากกว่า 60: 100 บาท

| Class | < 0 | 1–11 | 12–17 | 18–60 | > 60 |
|---|---|---|---|---|---|
| | Invalid | Valid: Free | Valid: 100 | Valid: 200 | Valid: 100 |

> ⚠️ สไลด์เขียน class แรกที่ valid เป็น "1–11" แต่ใน BVA (Exercise 5) ใช้ "0–11" — อายุ 0 ควรนับเป็นเด็ก (ฟรี) ตาม BVA

### 🔹 Boundary Value Analysis (BVA)
- **ขอบเขตมักเกิด error**
- ทดสอบ **ที่ขอบ** ไม่ใช่แค่สมาชิกใดก็ได้ของ class
- **วิธีออกแบบ:** ทำ ECP ก่อน แล้ว **เพิ่ม test case ที่ขอบ (boundary, +1, −1)**
- **Reduced cases:** มองขอบว่าอยู่ "ระหว่าง" ตัวเลข เช่น ขอบคือ 12 → แบบปกติ: 11, 12, 13 · แบบ reduced: 12, 13 (ขอบอยู่ระหว่าง 12 กับ 13)
- จำนวน case มาก (~3 ต่อ class)
- **ใช้ได้เฉพาะค่า ordinal** (เรียงลำดับได้ เป็นช่วง)

**ตัวอย่าง: Age Classification**
| Class | All Cases (ขอบล่าง / ขอบบน) | Belonging Cases | Reduced Class |
|---|---|---|---|
| Low | −1, 0 | −1 | −1 |
| 0–12 | −1,0,1 / 11,12,13 | 0,1 / 11,12 | 0, 12 |
| 13–19 | 12,13,14 / 18,19,20 | 13,14 / 18,19 | 13, 19 |
| 20–35 | 19,20,21 / 34,35,36 | 20,21 / 34,35 | 20, 35 |
| 36–120 | 35,36,37 / 119,120,121 | 36,37 / 119,120 | 36, 120 |
| High | 120, 121 | 121 | 121 |

**วิธีอ่านตาราง**
- **All Cases** = ขอบ −1, ขอบ, ขอบ +1 ทั้งด้านล่างและบน
- **Belonging Cases** = เฉพาะค่าใน All Cases ที่ **อยู่ใน class นั้นจริง**
- **Reduced Class** = เหลือแค่ **ค่าขอบล่างและขอบบนของ class** (ตัวเลขที่อยู่ติดขอบภายใน class)

**Exercise 4: 1–1000**
| Class | All Cases | Belonging | Reduced |
|---|---|---|---|
| < 1 | 0, 1 | 0 | 0 |
| 1–1000 | 0,1,2 / 999,1000,1001 | 1,2 / 999,1000 | 1, 1000 |
| > 1000 | 1000, 1001 | 1001 | 1001 |

Test cases: **0 (Invalid), 1 (Valid), 1000 (Valid), 1001 (Invalid)**

**Exercise 5: ค่าตั๋วอุทยาน (BVA + expected result)**
| Class | All Cases | Belonging | Reduced | Expected |
|---|---|---|---|---|
| Invalid (< 0) | −1, 0 | −1 | −1 | Error: Invalid Age |
| 0–11 | −1,0,1 / 10,11,12 | 0,1 / 10,11 | 0, 11 | Free |
| 12–17 | 11,12,13 / 16,17,18 | 12,13 / 16,17 | 12, 17 | 100 |
| 18–60 | 17,18,19 / 59,60,61 | 18,19 / 59,60 | 18, 60 | 200 |
| > 60 | 60, 61 | 61 | 61 | 100 |

> ⚠️ สไลด์เขียน class สุดท้ายว่า "> 61" แต่ตามโจทย์ควรเป็น **> 60** (ค่า 61 คือค่าแรกที่ได้ 100 บาท)

**Reduced test cases ทั้งหมด:** −1, 0, 11, 12, 17, 18, 60, 61

## 8. White-box Testing

- เรียกอีกชื่อ **glass-box / structural testing**
- ตรวจ **procedural detail** อย่างละเอียด (logical paths, การทำงานร่วมกันของ component)
- ใช้ **control structure** สร้าง test case
- สร้าง test case ที่:
  - **รับประกันว่าทุก independent path ใน module ถูกรันอย่างน้อย 1 ครั้ง**
  - ทดสอบ **ทุก logical decision ทั้งด้าน true และ false**
  - รัน **loop ที่ขอบเขต** และภายในขอบเขตการทำงาน
  - ทดสอบ **internal data structure** ว่าถูกต้อง

| | Black-box | White-box |
|---|---|---|
| ชื่ออื่น | behavioral, functional | glass-box, structural |
| ดูอะไร | spec / interface | โค้ด / control structure |
| เทคนิค | ECP, BVA | path analysis |

### 🔹 Path Analysis Technique
**2 งาน:** (1) วิเคราะห์ **จำนวน path** ในโปรแกรม (2) ตัดสินใจว่า **จะทดสอบ path ไหน**

**Coverage จากมากไปน้อย (decreasing coverage)**
1. **Logical paths** (ทุก path ที่เป็นไปได้)
2. **Independent paths**
3. **Branch coverage**
4. **Statement coverage**

### 🔹 ตัวอย่าง: if ธรรมดา
S1 → C1 → (true: S2) → S3 / (false) → S3
- path1: S1–C1–S3 (segments 1, 4)
- path2: S1–C1–S2–S3 (segments 1, 2, 3)

### 🔹 ตัวอย่าง: CASE structure (C1, C2, C3 เรียงซ้อน)
**4 independent paths:**
- path1: S1–C1–S2–S5
- path2: S1–C1–C2–S3–S5
- path3: S1–C1–C2–C3–S4–S5
- path4: S1–C1–C2–C3–S5

### 🔹 ตัวอย่าง: Loop
- path1: S1–C1–S3 (segments 1, 4) — ไม่เข้า loop
- path2: S1–C1–S2–C1–S3 (segments 1, 2, 3, 4) — เข้า loop 1 รอบ

### 🔹 Linearly Independent Set of Paths (3 ขั้นตอน — ทำใน Lab 10)
1. **คำนวณจำนวน independent paths = #Decision nodes + 1** (= cyclomatic number)
2. **List ทุก path ที่เป็นไปได้**
3. **เลือก linearly independent set of paths**

> 📌 **Linearly independent:** ชุดของ path ที่ **แต่ละ path เพิ่ม edge ใหม่อย่างน้อย 1 edge** ที่ไม่มีใน path ก่อนหน้า

```text
จำนวน independent paths (cyclomatic number) = จำนวน decision node + 1
จำนวน logical paths (decision แบบ binary เรียงกัน k ตัว) = 2^k
```

### 🧮 ตัวอย่าง: 3 decisions เรียงกัน (C1, C2, C3)
- แต่ละ binary decision มี 2 ทาง, เรียงกัน 3 ตัว → **2³ = 8 logical paths**:
  - path1: S1–C1–S2–C2–C3–S4
  - path2: S1–C1–S2–C2–C3–S5
  - path3: S1–C1–S2–C2–S3–C3–S4
  - path4: S1–C1–S2–C2–S3–C3–S5
  - path5: S1–C1–C2–C3–S4
  - path6: S1–C1–C2–C3–S5
  - path7: S1–C1–C2–S3–C3–S4
  - path8: S1–C1–C2–S3–C3–S5
- **Linearly independent = 3 decisions + 1 = 4**
- ชุดหนึ่งที่ใช้ได้ (ดูจาก segment):
  - path1: (1, 2, 4, 6, 9)
  - path2: (1, 2, 4, 6, 8) → ใหม่: 8
  - path3: (1, 2, 4, 5, 7, 9) → ใหม่: 5, 7
  - path5: (1, 3, 6, 9) → ใหม่: 3

**วิธีตรวจ:** ทำตาราง path × segment แล้วเช็กว่าทุก path ที่เพิ่มเข้ามามี segment ใหม่อย่างน้อย 1 ตัว และรวมกันครอบคลุมทุก segment

## 9. When to Stop Testing?
- **คำตอบง่าย:** หยุดเมื่อ **รัน test case ที่วางแผนไว้ครบ** และ **แก้ปัญหาที่พบครบ**
- **เทคนิคอื่น:**
  - หยุดเมื่อ **ไม่เจอ error เพิ่มแล้ว** (ดู **Problem Find Rate** = จำนวนปัญหาที่พบต่อชั่วโมง ที่ลดลงเรื่อย ๆ จากวันที่ 1 ถึง 5)
  - **Defect seeding** (ใส่ defect ไว้เองแล้วดูว่าหาเจอกี่ %)

## 10. Inspections vs Testing
| Inspections | Testing |
|---|---|
| **Cost-effective** | หา error ถูก แต่ **แก้แพง** |
| ใช้กับ **intermediate artifacts** ได้ (design, docs) | ใช้ได้ **กับโค้ดเท่านั้น** |
| **จับ defect เร็ว (early)** | จับ defect **ช้า** (หลัง implement) |
| ช่วย **กระจายความรู้** และ best practice | **จำเป็นในการวัดคุณภาพ** |
