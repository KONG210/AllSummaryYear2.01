## 1. Testing (ทบทวน)
- กิจกรรมตรวจว่าโค้ด (method, class, program) **ให้พฤติกรรมตามที่ตั้งใจ** หรือไม่
- กระบวนการประเมินซอฟต์แวร์เพื่อตรวจ **correctness, completeness, quality**
- **หา bug ตั้งแต่เนิ่น ๆ** ลดต้นทุนและเวลาในขั้นหลัง
- เพิ่ม **ความมั่นใจ** ใน reliability และ functionality

## 2. Test Phases

| Phase | ทดสอบอะไร | ขนาด/ความเร็ว | ต้นทุน | ความถี่ |
|---|---|---|---|---|
| **Unit testing** | **unit เดี่ยว** ของ source code (= ส่วนที่เล็กที่สุดที่ทดสอบได้) | เล็กสุด เร็วสุด | **ต่ำสุด** | **บ่อย** |
| **Integration testing** | **กลุ่มของ module** ที่รวมกัน | ปานกลาง | ปานกลาง | น้อยกว่า |
| **System testing** | **ระบบสมบูรณ์ที่รวมแล้ว** (ประเมินว่าตรง requirement) | ทั้งระบบ | **สูงสุด** | **ไม่บ่อย** |

## 3. Unit Testing
**เป้าหมาย:** ทำให้แน่ใจว่า **แต่ละ function ทำงานตามที่ตั้งใจก่อน integrate** กับส่วนอื่น

**Characteristics of Good Unit Tests**
| ลักษณะ | ความหมาย |
|---|---|
| **Focused / isolated** | แต่ละ test **โฟกัส function/method เดียว** ไม่พึ่งส่วนอื่น |
| **Fast** | รัน **เร็ว** เพื่อ test ต่อเนื่องระหว่างพัฒนา |
| **Automatable** | รัน **อัตโนมัติ** ใน **CI/CD pipeline** ได้ง่าย |
| **Repeatable / deterministic** | ได้ **ผลเหมือนเดิมทุกครั้ง** ไม่ขึ้นกับปัจจัยภายนอก |

### 🔹 JUnit
- พัฒนา **กลางยุค 90**
- เป็น **เครื่องมือมาตรฐานของ Test-Driven Development (TDD) ใน Java**
- JUnit test generator อยู่ใน Java IDE หลายตัว
- เครื่องมือ unit test Java อื่น ๆ: JMockit, Cactus, Cobertura, DbUnit, dJUnit ... (กว่า 30 tools)

**คุณสมบัติ**
- เป็นส่วนหนึ่งของ **unit testing frameworks**
- **link เป็น JAR ตอน compile**
- มี **Annotation** ระบุ test method และ **utility methods สำหรับ assert** ผลที่คาดหวัง
- มี **Test runners** สำหรับรัน test
- integrate กับ **Eclipse, Ant, Maven** ได้ง่าย

### 🔹 Annotation
- **tag ที่กำหนดไว้แล้ว** ใส่ในโค้ด บอก JUnit ว่าจะรัน test method เมื่อไหร่
- **`@Test`** — บอก JUnit ว่า method นี้ **รันเป็น test ได้**

### 🔹 Assertion
JUnit มีชุด **assertion methods** สำหรับเขียน test (สไลด์เป็นตารางรูปจาก tutorialspoint) ที่ใช้บ่อย:

| Method | ตรวจอะไร |
|---|---|
| `assertEquals(expected, actual)` | สองค่าเท่ากัน |
| `assertTrue(condition)` / `assertFalse(condition)` | เงื่อนไขเป็นจริง/เท็จ |
| `assertNull(obj)` / `assertNotNull(obj)` | เป็น/ไม่เป็น null |
| `assertSame(a, b)` / `assertNotSame(a, b)` | อ้างถึง object เดียวกัน/ไม่ใช่ |
| `assertArrayEquals(expected, actual)` | array เท่ากัน |

> ตารางนี้อ้างจาก JUnit ทั่วไป เพราะในไฟล์สไลด์เป็นรูปภาพ

### 🔹 JUnit Example (ตัวอย่างประกอบ)
```java
import org.junit.Test;
import static org.junit.Assert.assertEquals;

public class CalculatorTest {
    @Test
    public void testAdd() {
        Calculator c = new Calculator();
        assertEquals(5, c.add(2, 3));
    }
}
```
> ตัวอย่างในสไลด์เป็นรูป โค้ดข้างบนเป็นตัวอย่างรูปแบบเดียวกัน

## 4. Integration Testing
- ทดสอบ **การทำงานร่วมกันของ unit/component ที่รวมกัน** เพื่อหาปัญหาการสื่อสาร
- หาปัญหาใน **interface, data flow, dependencies** ระหว่าง component
- ตัวอย่าง: ทดสอบ function ที่ต้องใช้ **database connection** (ทั้งสองต้องทำงานร่วมกัน)
- **เชื่อมระหว่าง unit test กับ system test** โดยเน้นที่ "รอยต่อ"

### 🔹 เปรียบเทียบ 3 ระดับ
| | Module/Unit test | Integration test | System test |
|---|---|---|---|
| **Specification** | module interface | interface specs, module breakdown | **requirements specification** |
| **Visible structure** | **coding details** | **modular structure (software architecture)** | **— none —** |
| **Scaffolding required** | some | **often extensive** | some |
| **Looking for faults in** | modules | **interactions, compatibility** | **system functionality** |

### 🔹 Integration vs Unit Testing
- **Unit testing คือรากฐานที่จำเป็น**
  - ระดับ unit มี **controllability และ visibility สูงสุด**
  - **integration testing ชดเชย unit testing ที่ไม่พอไม่ได้เลย**
- integration testing ใช้เป็น **process check** ได้
  - ถ้า **พบ module fault ตอน integration** = unit testing **ไม่เพียงพอ**
  - ถ้าพบ fault ที่ **interface ระหว่าง module ที่ทำถูกแล้ว** = error มาจาก **module breakdown และ interface specifications**

## 5. System Testing
- ทดสอบ **ระบบสมบูรณ์** ว่าตรง **functional และ non-functional requirements**
- ทำให้แน่ใจว่าระบบ **ทำงานเป็นภาพรวม** และ **ทำงานตามคาดในสถานการณ์จริง**

**ประเภท**
| ประเภท | ตรวจอะไร |
|---|---|
| **Functional Testing** | ระบบ **ทำ function ที่คาดไว้** |
| **Non-functional Testing** | **performance, usability, reliability** |
| **Security Testing** | **ช่องโหว่** ที่อาจมี |

### 🔹 เอกสารประกอบ (สไลด์เป็นรูปตัวอย่าง)
- **Test case template** — รายละเอียด test case (ID, ขั้นตอน, ข้อมูล, ผลที่คาด, ผลจริง, สถานะ)
- **Test Report** — สรุปผลการทดสอบ
- **Traceability Record (Requirement Traceability Matrix, RTM)** — เชื่อม **requirement ↔ test case** ว่าทุก requirement ถูกทดสอบ

## 6. Regression Testing
- ทดสอบว่า **การแก้โค้ดล่าสุดไม่ทำให้เกิด bug ใหม่** หรือ **ทำให้ฟังก์ชันเดิมถดถอย**
- ยืนยันว่า update (bug fix, feature ใหม่) **ไม่รบกวนส่วนที่เคยทำงานได้**
- มักรัน **หลังแก้โค้ด** ทั้ง fix, enhancement, optimization
- เพิ่ม feature ใหม่ → regression test ยืนยันว่าไม่กระทบส่วนอื่นโดยไม่ตั้งใจ

**เมื่อไหร่ใช้:** หลัง **bug fixes** · หลัง **new features / enhancement** · หลัง **performance improvements** · ระหว่าง **routine maintenance**

## 7. Software Quality Models และ Usability
(สไลด์ Software Quality Models เป็นรูปของ quality attributes)

> 📌 **Usability** = ความง่ายและมีประสิทธิภาพที่ผู้ใช้โต้ตอบกับซอฟต์แวร์เพื่อบรรลุเป้าหมาย

- ซอฟต์แวร์ใช้ง่าย **มีโอกาสถูกนำไปใช้มากกว่า**
- เพิ่ม productivity ด้วยการลดเวลาและแรงในการทำงาน
- **Usability มี 5 components** (สไลด์เป็นรูป — ตามนิยามของ Nielsen ที่ใช้กันทั่วไปคือ **Learnability, Efficiency, Memorability, Errors, Satisfaction**)

### 🔹 Usability testing
- ประเมินผลิตภัณฑ์โดย **ให้ผู้ใช้ในอนาคตทดลองใช้** ได้ข้อมูลตรงว่าเขาใช้ระบบอย่างไร
- ตรวจว่าผลิตภัณฑ์ **ตรงเป้าหมายและ requirement** ที่ตั้งไว้

**Common Methods**
| Method | วิธี |
|---|---|
| **Task-Based Testing** | ผู้ใช้ทำ task ที่กำหนด ผู้สังเกตหาจุดที่ติดขัด (pain points) |
| **A/B Testing** | **เปรียบเทียบ 2 design** ว่าแบบไหนดีกว่า |
| **Surveys and Questionnaires** | เก็บ feedback ความพึงพอใจและความง่ายในการใช้ |

### 🔹 Performance Measurement (ข้อมูลเชิงปริมาณ)
- **เวลา** ที่ผู้ใช้ใช้ทำ task หนึ่ง
- **จำนวน task** ที่ทำได้ในเวลาที่กำหนด
- **อัตราส่วน** การโต้ตอบที่สำเร็จต่อ error
- เวลาที่ใช้ **กู้คืนจาก error**
- **จำนวน error** ของผู้ใช้
- จำนวนคำสั่ง/ฟีเจอร์ที่ **ไม่เคยถูกใช้**
- ความถี่ในการใช้ **คู่มือ/help** และเวลาที่ใช้

## 8. Best Practices in Testing
- ทำโค้ดให้ **modular และ isolated** เพื่อให้ test ง่าย
- รวม testing เข้ากับ **CI/CD pipeline** เพื่อคุณภาพต่อเนื่อง
- **test สม่ำเสมอ** ลดความเสี่ยงที่ bug หลุด
- **จำลอง dependencies** (mock/stub) ให้ test มีประสิทธิภาพ
- ใช้ **coverage metrics** ดูว่าทดสอบไปเท่าไร โดยเน้น **coverage ที่มีความหมาย มากกว่าไล่ให้ถึง 100%**

**โจทย์:** < 500 ไม่ลด · 500–999 ลด 5% · 1,000–4,999 ลด 10% · > 5,000 ลด 20% · > 100,000 invalid

**เฉลยในสไลด์**
| Class | Representative | Expected |
|---|---|---|
| ≤ 0 | −5 | Invalid input |
| 1 – 500 | 450 | No discount |
| 501 – 999 | 658 | 5% discount |
| 1,000 – 4,999 | 2,599 | 10% discount |
| 5,000 – 100,000 | 45,100 | 20% discount |
| > 100,000 | 111,111 | Invalid input |

> ⚠️ **เฉลยในสไลด์ไม่ตรงกับโจทย์ที่ขอบ:** โจทย์บอก "500–999 ลด 5%" แต่เฉลยจัด 500 ไว้ใน "ไม่ลด" (1–500) · และโจทย์บอก "> 5,000 ลด 20%" แต่เฉลยจัด 5,000 ไว้ใน 20% (ทั้งที่ 1,000–4,999 คือ 10% ทำให้ 5,000 ไม่อยู่ในช่วงไหนตามโจทย์) — ตอนสอบให้ **อ่านโจทย์และกำหนดขอบให้สอดคล้องกัน** ถ้าโจทย์ตามตัวอักษร class ควรเป็น ≤0 / 1–499 / 500–999 / 1,000–4,999 / 5,000(หรือ 5,001)–100,000 / >100,000
