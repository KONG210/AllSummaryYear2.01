## 1. Programming Paradigms

| Paradigm | แนวคิด | ตัวอย่างภาษา |
|---|---|---|
| **Imperative** | บอกคอมพิวเตอร์ **ว่าทำอย่างไร ทีละขั้น** | C, Python, Java, JavaScript |
| **Declarative** | ระบุ **ว่าต้องการอะไร ไม่ใช่ทำอย่างไร** | **SQL** |
| **Object-oriented** | จำลองซอฟต์แวร์เป็น **object** ที่มีข้อมูล (attributes) และพฤติกรรม (methods) | Java, Python, C++, C#, Ruby |
| **Logic** | นิยาม **ว่าปัญหาคืออะไร** ไม่ใช่วิธีแก้ | **Prolog** |

- บางภาษารองรับหลาย paradigm = **multi-paradigm languages**

### 🔹 Emerging Development Approaches
| | No-code | Low-code | Vibe coding |
|---|---|---|---|
| คืออะไร | สร้างแอป **โดยไม่เขียนโค้ดเลย** ใช้ GUI, drag-and-drop, logic block สำเร็จรูป | สร้างแอปด้วย **โค้ดน้อยที่สุด** ใช้ visual tools และเขียนโค้ดเพิ่มได้เมื่อจำเป็น (เช่น Mendix) | สร้างโปรแกรมโดย **อธิบายสิ่งที่ต้องการด้วยภาษาธรรมชาติ** ผสม AI, visual design, live feedback |
| Benefits | เร็ว, ไม่ต้องมีพื้นเทคนิคมาก, ทดลอง/prototype ง่าย | เร็วกว่าเขียนเอง, **สมดุลระหว่างง่ายกับยืดหยุ่น** | ไม่ต้องมีพื้นเทคนิคมาก, interactive และเร็ว |
| Limitations | logic ซับซ้อนทำยาก, **ผูกกับ platform**, scale/customize ลึกยาก | **ต้องมีความรู้เทคนิคบ้าง**, customize ซับซ้อนดูแลยาก, ผูกกับ platform | logic ซับซ้อนทำยาก, ผูกกับ platform, **พึ่ง AI มากเกินไป** |

## 2. Implementation

> "Any fool can write code that a computer can understand. **Good programmers write code that humans can understand.**" — M. Fowler (1999)

> 📌 **Implementation:** การแปลง **detailed designs เป็นโปรแกรมที่ถูกต้อง**

## 3. Style Guides and Rules

- องค์กรส่วนใหญ่มี **กฎควบคุม codebase**: ที่เก็บ source file, การจัดรูปแบบโค้ด, การตั้งชื่อ, patterns, exceptions, threads
- วิศวกรส่วนใหญ่ทำงานภายใต้ policy เหล่านี้
- องค์กรควรมี **style guides** ที่กำหนดกฎ

### 🔹 ทำไมต้องมีกฎ?
- เพื่อ **ส่งเสริมพฤติกรรม "ดี" และลดพฤติกรรม "ไม่ดี"**
- "ดี/ไม่ดี" **ต่างกันในแต่ละองค์กร** ขึ้นกับสิ่งที่องค์กรให้ความสำคัญ เช่น
  - ประหยัด memory หรือ optimize runtime
  - ใช้ฟีเจอร์ใหม่ของภาษา
  - **ความสม่ำเสมอ (consistency)** — อะไรที่ไม่เข้ากับ pattern เดิมถือว่า "ไม่ดี"

### 🔹 Style guide มี 3 ประเภทกฎ
| ประเภท | ตัวอย่าง |
|---|---|
| **Rules to avoid dangers** | การใช้ static members/variables, lambda, **การจัดการ exception** (เช่น Google Java guide เรื่อง caught exceptions ห้ามละเลย), threading, access control, class inheritance, vocabulary types ที่ใช้ได้, สิ่งที่ใช้ยากหรือใช้ให้ถูกยาก |
| **Rules to enforce best practices** | ช่วยให้ codebase แข็งแรงดูแลง่าย เช่น **กำหนดว่าต้องเขียน comment ที่ไหนอย่างไร** |
| **Rules to ensure consistency** | ให้คนเขียนและคนอ่าน **โฟกัสที่สิ่งที่โค้ดทำ ไม่ใช่การจัดหน้า** |

**ประโยชน์ของ consistency**
1. **Consistency enables scaling** — สร้าง tool ช่วยนักพัฒนาง่ายขึ้น
2. **ช่วย human scaling** — ย้ายข้ามโปรเจกต์ได้ง่าย
3. **ทนต่อกาลเวลา (resilience to time)**

### 🔹 Good Implementation Practices
| Practice | ความหมาย |
|---|---|
| **Keep functions small and focused** | 1 function ทำ 1 อย่าง ถ้าต้อง scroll อ่านแปลว่าทำมากเกิน (ดู **Extract Method** refactoring) |
| **Do not repeat yourself (DRY)** | logic ซ้ำเป็นแหล่ง bug — ถ้าต้องแก้ 3 ที่ อาจแก้แค่ 2 แล้วลืมที่ 3 |
| **Write code for the reader, not the compiler** | compiler ไม่สนชื่อหรือโครงสร้าง แต่เพื่อนที่แก้ bug ตอนตี 2 สน |
| **Handle errors explicitly** | อย่าเงียบเฉยต่อ exception หรือ return null โดยไม่บอก ทุก error path คือการตัดสินใจที่ต้องมองเห็นได้ |
| **Commit small and often** | commit เล็ก review ง่าย หา bug ง่าย ลดความเสี่ยงงานหาย |
| **Test as you write, not after** | เขียน test ทีหลังมักทดสอบ "สิ่งที่โค้ดทำ" แทน "สิ่งที่โค้ดควรทำ" |

## 4. Code Comments — 9 Rules (Ellen Spertus)

| Rule | ความหมาย | ตัวอย่าง/คำอธิบาย |
|---|---|---|
| **1** | Comments should **not duplicate the code** | ❌ `i = i + 1; // add 1 to i` |
| **2** | Good comments **do not excuse unclear code** | ตั้งชื่อตัวแปรให้ดีดีกว่าเขียน comment อธิบายชื่อแย่ ๆ |
| **3** | If you **can't write a clear comment**, there may be a **problem with the code** | อธิบายไม่ได้ = โค้ดซับซ้อนเกิน ควร refactor |
| **4** | Comments should **dispel confusion, not cause it** | comment ต้องทำให้เข้าใจขึ้น |
| **5** | **Explain unidiomatic code** in comments | โค้ดที่เขียนแปลกจากปกติต้องบอกเหตุผล ไม่งั้นคนอื่นจะ "แก้" ให้ปกติแล้วพัง |
| **6** | Provide **links to the original source of copied code** | `/** Converts a Drawable to Bitmap. via https://stackoverflow.com/a/46018816/2219998. */` → คนอ่านตามไปดูได้ว่าแก้ปัญหาอะไร ใครเขียน ทำไมแนะนำ คนอื่นว่าอย่างไร ยังใช้ได้ไหม ปรับปรุงยังไง |
| **7** | Include **links to external references** where most helpful | `// Many thanks to Chris Veness at http://www.movable-type.co.uk/scripts/latlong.html for a great reference and examples.` |
| **8** | **Add comments when fixing bugs** | อธิบายว่าแก้อะไร ทำไม |
| **9** | Use comments to **mark incomplete implementations** | `// TODO(hal): We are making the decimal separator be a period, regardless of the locale of the phone. We need to think about how to allow comma as decimal separator...` |

## 5. Debugging

> 📌 **Debugging** = การหาตำแหน่งและแก้ error ในโค้ด; error ถูกสังเกตจาก testing, inspection, หรือการใช้งาน

**4 Phases**
1. **Stabilization (reproduction)** — ทำให้ bug เกิดซ้ำได้
2. **Localization** — หาตำแหน่งที่ผิด
3. **Correction** — แก้
4. **Verification** — ยืนยันว่าแก้ได้จริงและไม่ทำให้อย่างอื่นพัง

**Heuristics**
- บาง routine จะมี error เยอะ
- **routine ที่มี error มักมี error เพิ่มอีก**
- **โค้ดใหม่มักมี error มากกว่า**
- บางภาษา บางส่วน บาง coder มี error มากเป็นพิเศษ

**Tools:** code comparators · extended checkers (**lint**) · **interactive debuggers** · special libraries · อื่น ๆ: profilers, pre/post conditions, test coverage

## 6. Refactoring

> 📌 "Refactoring is the process of changing a software system in such a way that it **does not alter the external behavior** of the code yet **improves its internal structure**." — Martin Fowler
> = ศิลปะในการปรับปรุง design ของโค้ดที่มีอยู่ **อย่างปลอดภัย**

**ข้อสังเกต (implications)**
- refactoring **ไม่ใช่การเปลี่ยนแปลงอะไรก็ได้** ในระบบ
- refactoring **ไม่ใช่การเขียนใหม่ตั้งแต่ต้น**
- refactoring **ไม่ใช่แค่การจัดโครงสร้างใหม่ใด ๆ** ที่ตั้งใจปรับปรุงโค้ด
- refactoring **สนับสนุน emergent design** (design ที่ค่อย ๆ เกิดขึ้น)
- refactoring **เล็กหรือใหญ่ก็ได้**

| Code Smells (สัญญาณโค้ดมีปัญหา) | Refactoring Actions |
|---|---|
| Duplicated code | **Extract method** |
| Long method | Substitute algorithm |
| Large class | Move method |
| Switch statement | **Extract class** |
| Feature envy (method สนใจข้อมูล class อื่นมากกว่าของตัวเอง) | ... อีกมาก (refactoring.com/catalog) |
| Intimacy (class รู้รายละเอียดภายในของกันมากเกิน) | |

อ้างอิง: *Refactoring* 2nd ed. (Fowler), *Refactoring in Ruby* (Wake & Rutherford)

## 7. Code Inspection (Fagan)

- เสนอโดย **Michael Fagan (IBM) ตั้งแต่ 1976**
  - เพื่อ **ปรับปรุงคุณภาพซอฟต์แวร์**
  - เพื่อ **เพิ่ม productivity ของโปรแกรมเมอร์**
- **มีประสิทธิภาพในการหา defect** และใช้มากที่ IBM
- ทำได้กับ **code, design artifacts, requirements, user information, documentation, test plans และ test cases**

### 🔹 Inspection Process (6 ขั้น — ต้องจำ)
| ขั้น | Objective |
|---|---|
| **1. Planning** | เอกสารที่จะตรวจต้องผ่าน **entry criteria**; จัดหา **ผู้เข้าร่วม** ที่เหมาะสม; จัด **สถานที่และเวลา** |
| **2. Overview** | **ให้ความรู้กลุ่ม** ว่าจะตรวจอะไร; **มอบหมายบทบาท (roles)** |
| **3. Preparation** | ผู้เข้าร่วม **ศึกษาเอกสาร** และเตรียมทำหน้าที่ตามบทบาท |
| **4. Inspection** | **หา defects** — **ไม่สนับสนุนการหาวิธีแก้หรือถกเรื่อง design ทางเลือก** |
| **5. Rework** | **ผู้เขียน (author) แก้ defect ทั้งหมด** |
| **6. Follow-up** | **moderator** หรือทั้งทีม **ตรวจยืนยัน** ว่าแก้ได้ผลทั้งหมดและไม่เกิด defect ใหม่ (secondary defects) |

> ⚠️ ขั้น Inspection = **หา** defect เท่านั้น ไม่แก้ ไม่ถกวิธีแก้

## 8. Modern Code Review

- ต่างจาก code inspection ตรงที่ **ทำผ่าน modern code review tools** (เช่น pull request บน GitHub/GitLab, Gerrit)
- ตัวอย่าง: reviewer ใส่ comment ที่บรรทัดโค้ดใน pull request

### 🔹 Benefits of Code Review (Google) — 6 ข้อ
1. **ตรวจความถูกต้องของโค้ด**
2. ทำให้แน่ใจว่าการเปลี่ยนแปลง **คนอื่นเข้าใจได้**
3. **บังคับ consistency** ทั่ว codebase
4. **ส่งเสริม team ownership** ทางจิตวิทยา
5. **แบ่งปันความรู้ (knowledge sharing)**
6. **มีบันทึกประวัติ** ของการ review

### 🔹 Code Review Checklist (Michaela Greiler)
| หมวด | คำถาม |
|---|---|
| **Implementation** | ทำสิ่งที่ควรทำไหม? ทำให้ง่ายกว่านี้ได้ไหม? เพิ่ม dependency ที่ไม่ต้องการ (compile/run-time) ไหม? |
| **Dependencies** | ต้องอัปเดตนอกโค้ด (docs, config, readme) ทำแล้วหรือยัง? กระทบส่วนอื่นหรือ backward compatibility ไหม? |
| **Security & Data Privacy** | เปิดช่องโหว่ไหม? จัดการ authorization/authentication ถูกต้องไหม? ข้อมูลอ่อนไหว (ข้อมูลผู้ใช้ บัตรเครดิต) เก็บอย่างปลอดภัยไหม? |
| **Logic Errors & Bugs** | มี use case ที่ทำงานผิดไหม? input หรือเหตุการณ์ภายนอกที่ทำให้พังไหม? |
| **Error Handling & Logging** | จัดการ error ถูกต้องไหม? ควรเพิ่ม/ลบ log ไหม? error message เป็นมิตรไหม? |
| **Testing & Testability** | test ได้ไหม? มี automated test (unit/integration/system) พอไหม? |
| **Readability** | เข้าใจง่ายไหม? ส่วนไหนงง ทำไม? แยก method เล็กลงจะอ่านง่ายขึ้นไหม? |
| **Usability & Accessibility** | ออกแบบดีในมุม usability ไหม? API มีเอกสารดีไหม? |
| **Performance** | กระทบ performance ทางลบไหม? ปรับให้เร็วขึ้นได้ไหม? |
| **Experts Opinion** | ควรให้ผู้เชี่ยวชาญ (security, usability) ดูไหม? กระทบทีมอื่นไหม? ทีมนั้นควรมีส่วนร่วมไหม? |

### 🔹 Discussion: Code Review in Practice
**Scenario:** junior ส่ง PR แก้ bug — โค้ดทำงานถูก แต่:
- ตัวแปรชื่อ `x` เก็บยอดเงินในบัญชี
- ไม่มี comment อธิบายว่าทำไม fix นี้ใช้ได้
- logic เดียวกันอยู่ในอีก 2 method
- ไม่มี unit test สำหรับ bug fix

**แนวคำตอบ** (สไลด์ให้คิดเอง ไม่ได้เฉลย)
1. **ยังไม่ควร approve** เพราะแม้ทำงานถูกแต่มีปัญหาด้านอ่านง่าย ดูแลง่าย และไม่มี test
2. Checklist ที่เกี่ยว: **Readability** (ชื่อ `x`), **Testing** (ไม่มี unit test), DRY/maintainability (logic ซ้ำ), comment rule 8 (comment ตอนแก้ bug)
3. Comment ด้วยน้ำเสียง **สุภาพ สร้างสรรค์ อธิบายเหตุผล** เช่น "ขอบคุณที่แก้ bug นี้ครับ รบกวนเปลี่ยนชื่อ `x` เป็น `accountBalance` และเพิ่ม unit test ที่ reproduce bug นี้ได้ไหมครับ จะช่วยกันไม่ให้ bug กลับมา"
4. ขั้นต่ำก่อน approve: **ตั้งชื่อตัวแปรให้สื่อความหมาย + เพิ่ม unit test** (ส่วน logic ซ้ำอาจแยกเป็น PR ถัดไปได้)

## Conclusion
Good implementation คือการเขียนโค้ดที่คนอื่น **อ่าน ดูแล และไว้ใจได้** ไม่ใช่แค่รันได้
- สมดุล readability, correctness, maintainability, performance, traceability, completeness
- style guide ทำให้ codebase สม่ำเสมอข้ามทีม
- comment อธิบาย **เจตนา (intent)** ไม่ใช่ทวนโค้ด
- refactoring ปรับโครงสร้างภายในโดยไม่เปลี่ยนพฤติกรรม
- debugging เป็นระบบ: **stabilize, localize, correct, verify**
- code review เป็นความรับผิดชอบร่วม: จับ bug, กระจายความรู้, สร้าง team ownership
- 2 คำถามก่อน commit: **ถ้า team lead อ่านตอนนี้จะสบายใจไหม?** · **อีก 6 เดือนเราจะเข้าใจโค้ดนี้โดยไม่มี context ไหม?**
