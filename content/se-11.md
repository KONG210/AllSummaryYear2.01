## 1. Software Configuration Management (CM)

> 📌 **Software Configuration Management** ครอบคลุมศาสตร์และเทคนิคในการ **เริ่มต้น ประเมิน และควบคุมการเปลี่ยนแปลง** ของผลิตภัณฑ์ซอฟต์แวร์ **ระหว่างและหลัง** กระบวนการพัฒนา

**มาตรฐาน**
- **IEEE 828:** Software Configuration Management Plans
- **IEEE 1042:** Guide to Software Configuration Management

(สไลด์แสดงแผนภาพ configuration management process จาก Elliando Dias, 2008 — เป็นรูป)

### 🔹 Configuration item
- ชิ้นส่วนซอฟต์แวร์ เอกสาร ฮาร์ดแวร์ หรือผลงานใด ๆ **ที่เปลี่ยนแปลงได้** = configuration item
- คือ **"สิ่ง" ที่เราอยากติดตามและควบคุม**
- **เกือบทุกอย่างเป็น configuration item ได้** ไม่ใช่แค่โค้ด:
  - code files ทุกชนิด
  - **drivers for tests**
  - เอกสาร requirement, analysis, design
  - คู่มือผู้ใช้/นักพัฒนา
  - **system configurations** (เช่น เวอร์ชันของ compiler ที่ใช้)
  - **hardware configuration items** (CPU, bus speed)

### 🔹 Version identification
ต้องมีวิธีระบุเวอร์ชันของ component **อย่างไม่กำกวม**

| เทคนิค | วิธี | ข้อสังเกต |
|---|---|---|
| **1) Version numbering** | ตั้งชื่อแบบ **linear derivation** เช่น V1, V1.1, V1.2, V2.1, V2.2 | ง่าย แต่ **ชื่อไม่มีความหมาย** |
| **2) Attribute-based identification** | ใช้ **ชุดของ attribute** ระบุเวอร์ชัน | attribute เช่น **Date, Creator, Programming Language, Customer, Status** |

## 2. Version Control System (VCS)

ปัญหา: "Losing track of your changes?" — ไม่รู้ว่าแก้อะไรไปตอนไหน กู้คืนไม่ได้

- VCS เป็น **ส่วนประกอบหนึ่งของ configuration management**
- **วัตถุประสงค์ 3 ข้อ**
  1. **Restoring previous configurations** — กู้คืนเวอร์ชันก่อนหน้า
  2. **Coordinating changes** — ประสานการแก้ไขของหลายคน
  3. **Identifying versions and components** — ระบุเวอร์ชันและส่วนประกอบ

(สไลด์แสดงประเภท VCS: local, centralized, distributed — เป็นรูป)

| | Centralized VCS (เช่น Subversion, CVS) | Distributed VCS (เช่น Git) |
|---|---|---|
| repository | มีศูนย์กลางที่เดียว | **ทุกคนมี repository ครบ** |
| ทำงาน offline | ไม่ได้เป็นส่วนใหญ่ | **ได้เกือบทุก operation** |

> ตารางนี้เป็นการเปรียบเทียบทั่วไปประกอบรูปในสไลด์

## 3. Git

> 📌 **Git** = **free and open-source distributed version control system** ออกแบบให้รองรับตั้งแต่โปรเจกต์เล็กถึงใหญ่มาก **อย่างรวดเร็วและมีประสิทธิภาพ** (git-scm.com)

- เรียนรู้ง่าย
- **footprint เล็ก ประสิทธิภาพเร็วมาก**
- เหนือกว่า SCM tool อื่นอย่าง **Subversion และ CVS**
- **local branching ราคาถูก**, **staging area** สะดวก, รองรับหลาย workflow

### 🔹 Distributed Version Control (คุณสมบัติ)
- **เกือบทุกอย่างอยู่ในเครื่อง (local)**
- เกือบทุก operation **เร็ว**
- **ทุก repository ที่ clone เป็น backup**
- เกือบทุก operation **ทำงาน offline ได้**
- เกือบทุก repository **มีประวัติครบ (full history)**

### 🔹 Git's Special: Staging Area
- ต่างจาก VCS อื่น Git มีแนวคิด **staging area (index)**
- คือ **การเปลี่ยนแปลงที่จะถูก commit**
- ใช้ **เตรียม** ก่อน commit

```text
Working directory --git add--> Staging area --git commit--> Local repository
Local repository  --git push--> Remote repository
Remote repository --git pull--> Local repository (+ working directory)
```

### 🔹 Operations หลัก
| คำสั่ง | ทำอะไร |
|---|---|
| **add** (`git add <file>`) | เพิ่มการเปลี่ยนแปลงที่เลือกจาก **working directory → staging area**; กำหนดว่าอะไรจะอยู่ใน commit ถัดไป; **review ได้ก่อน commit** |
| **commit** (`git commit -m "message"`) | เพิ่มสิ่งที่ stage แล้ว **→ local repository**; สร้าง **เวอร์ชันใหม่ (commit)**; มี **commit message** อธิบาย |
| **pull** | นำการเปลี่ยนแปลงจาก **remote → local**; **fetch แล้ว merge** เข้า branch ปัจจุบัน; merge ส่วนใหญ่อัตโนมัติ; **conflict เกิดได้แต่จัดการไม่ยาก** |
| **push** | ส่ง local commits **→ remote repository**; ให้คนอื่นเห็นการเปลี่ยนแปลง; **อาจถูก reject ถ้า remote มีการเปลี่ยนแปลงที่ local ยังไม่มี** (ต้อง pull ก่อน) |

**นอก push/pull:** Git **สร้าง patch** และ **integrate patch** ได้

### 🔹 Decentralized but Centralized
Git เป็น distributed แต่ในทางปฏิบัติทีมมักมี **repository กลาง (origin)** ที่ทุกคน push/pull และนักพัฒนา push/pull กันเองได้ด้วย

## 4. Branches

- Git มี branch เริ่มต้นชื่อ **"master"** (ปัจจุบันมักชื่อ main)
- **master ต้อง deployable** = production code พร้อมปล่อย
- **master ต้องเสถียร**
- **สัญญาทางสังคมของ open-source:** **ห้าม push สิ่งที่ยังไม่ test หรือทำให้ build พังเข้า master เด็ดขาด**
- GitHub ใช้ได้ดีเพราะ **ทำงานจาก master ได้อย่างปลอดภัยเสมอ**

### 🔹 เมื่อไหร่ควรสร้าง branch ใหม่?
- **เพิ่ม feature ใหม่**
- ทำ **release ใหม่**
- **ทดลอง** การเปลี่ยนแปลง
- **แก้ bug**

### 🔹 Branching and Merging
- branching/merging ใน Git **ง่าย**
- branch มัก **ชั่วคราว**
- **สนับสนุนให้แตก branch**
- merge ส่วนใหญ่ **อัตโนมัติ**
- แต่ branching อาจทำให้เกิด **conflict ตอน merge**
- แก้ conflict โดยไม่มี tool ช่วย **เจ็บปวด**
- ควร **ใช้ workflow ที่กำหนดไว้**

## 5. Git Branching Model (Vincent Driessen, nvie.com)

### 🔹 Main branches (มีตลอด)
| Branch | สะท้อนสถานะ |
|---|---|
| **master** | source code **พร้อม production เสมอ** |
| **develop** | การเปลี่ยนแปลงล่าสุดที่ **พัฒนาเสร็จสำหรับ release ถัดไป** |

### 🔹 Supporting branches (ชั่วคราว)
| Branch | ใช้ทำอะไร | แตกจาก → merge กลับ |
|---|---|---|
| **Feature** (topic) | พัฒนา **feature ใหม่** สำหรับ release ถัดไปหรือในอนาคต | develop → develop |
| **Release** | **เตรียม production release ใหม่**; ทำให้ develop ว่างรับ feature ของ release ถัดไป | develop → master และ develop |
| **Hotfix** | แก้ **bug วิกฤตใน production ทันที**; แตกจาก **tag บน master** ที่ระบุเวอร์ชัน production | master → master และ develop |

> คอลัมน์ "แตกจาก → merge กลับ" มาจากแผนภาพ "The Whole Picture" ของ branching model นี้ (สไลด์ข้อความระบุชัดแค่ hotfix แตกจาก tag บน master)

```text
master  ──●───────────────●─────────●──   (tag v1.0, v1.1 ...)
           \ hotfix ──●──/│         ↑
develop ────●──●──────●──●──●───────┤
             \feature/       \release/
```
