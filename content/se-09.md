# L9 · Design, Architecture and Methodology

## ภาพรวมของบท

**หัวข้อ:** Architectural vs detailed design · เทคนิคพื้นฐานของ detailed design · หลักการออกแบบทางวิศวกรรมซอฟต์แวร์ · ลักษณะของการออกแบบที่ดี

> 🔗 ภาพใหญ่: เริ่มจาก **requirements** → ตัดสินใจโครงสร้างใหญ่ (**architectural design**: มีส่วนประกอบอะไร เชื่อมกันยังไง เลือก **architectural style**) → ลงรายละเอียด (**detailed design**: class, algorithm, data structure) → แปลง DFD เป็น structure chart ด้วย **transform mapping** → ประเมินว่าดีไหมด้วย **design principles** (โดยเฉพาะ **cohesion สูง coupling ต่ำ**)

สไลด์เปิดด้วยภาพสะพานหลายแบบ (สะพานมีหลายแบบตามงาน = ซอฟต์แวร์ก็มีหลายสถาปัตยกรรม) และ "How to write HelloWorld" (ภาพตัวอย่างหลายวิธี — เนื้อหาเป็นรูป อ่านจากไฟล์ไม่ได้)

## 1. Design Architecture and Methodology

- **เริ่มจาก requirements**
- ซอฟต์แวร์จะมี **โครงสร้าง** อย่างไร: มี **component** อะไร, component **สัมพันธ์กัน** อย่างไร
- แบ่งเป็น 2 ส่วน: **Architectural (high-level) design** และ **Detailed design**
- **Detailed design มาจาก requirements และ architecture**
- Analysis Model → Design Model (อ้างอิง Pressman)
- ตัวอย่างเปรียบเทียบ: ลูกค้าบอก "4 ห้องนอน 3 ห้องน้ำ กระจกเยอะ ๆ" (requirements) → architectural design (แบบบ้าน) → implementation — ถ้าข้ามขั้นออกแบบไปสร้างเลยแล้วออกมาดีก็คือ "It's a miracle!"

### 🔹 Architectural Design
> 📌 **Definition:** กิจกรรมการระบุ **ส่วนหลักของโปรแกรม** (major parts); **หน้าที่ คุณสมบัติ และ interface** ของแต่ละส่วน; และ **ความสัมพันธ์/การโต้ตอบ** ระหว่างส่วนเหล่านั้น

**Key components:** Layers & Modules · Components & Services · Data Flow & Storage · Security & Performance · Scalability & Maintainability · Integration & APIs

### 🔹 Detailed Design
> 📌 **Definition:** ลงลึกใน component แต่ละตัว ระบุ **element ภายใน** และ **ความสัมพันธ์ระหว่างกัน** รวมถึง **data structures และ algorithm specifications**

**Key components:** Module-Level Design · Class & Object Design · Function & Algorithm Design · Database Schema · Interface & API Design · Error Handling & Logging · Security Considerations

| | Architectural | Detailed |
|---|---|---|
| ระดับ | high-level ทั้งระบบ | ภายใน component |
| ตัดสินใจเรื่อง | ส่วนหลัก, หน้าที่, interface, ความสัมพันธ์ | class, algorithm, data structure, schema |

### 🔹 Exercise: Architectural หรือ Detailed?
| ข้อ | ข้อความ | แนวคำตอบ | เหตุผล |
|---|---|---|---|
| 1 | find() ต้องใช้ binary search | **Detailed** | ระบุ algorithm |
| 2 | ต้องแยกโค้ด UI ออกจากโค้ดส่วนอื่น | **Architectural** | แบ่งส่วนหลักของระบบ |
| 3 | client ประมวลผล ≤ 1 วิ, server ≤ 0.5 วิ | **Architectural** | คุณสมบัติ (performance) ของส่วนหลัก |
| 4 | Register class ต้องเก็บ client ใน hash table | **Detailed** | ระบุ data structure ใน class |
| 5 | ทุก utility ใน graphics library ต้อง thread-safe | **Architectural** | คุณสมบัติของ component หลัก |
| 6 | Car ทุกตัวลงทะเบียนกับ Clock และ Clock แจ้งทุกวินาที | **Detailed** | การโต้ตอบระดับ object |
| 7 | observer ของ Clock ต้อง implement ClockUser | **Detailed** | การออกแบบระดับ class/interface |

> ⚠️ สไลด์ไม่ได้ให้เฉลย ตารางนี้เป็นแนวคำตอบตามนิยาม — เช็กกับเฉลยในห้อง

## 2. Architectural Styles

### 🔹 1) Batch Sequential / Pipe and Filter
**คืออะไร:** ข้อมูลเข้าระบบ แล้วผ่าน **การแปลงต่อเนื่องเป็นชุด** ก่อนได้ output — ส่งข้อมูลด้วย **pipes** และแปลงด้วย **filters**

| Pros | Cons |
|---|---|
| ใช้ filter เดิมซ้ำสร้าง configuration ใหม่ได้ (**reusability**) | **ไม่เหมาะกับแอป interactive** เพราะได้ output หลังผ่านการแปลงทั้งชุด |
| เหมาะกับงานที่ต้องคำนวณอิสระต่อกันเป็นลำดับชัดเจน | อาจต้องเพิ่ม filter ให้ component เข้ากันได้ |
| | ถ้า component ไม่ได้ออกแบบอิสระ อาจเกิด **tight coupling** |

**ตัวอย่าง:** compiler (lexer → parser → optimizer → code gen), คำสั่ง `cat file | grep x | sort`

### 🔹 2) Data-centered Architecture
**คืออะไร:** ข้อมูลที่ใช้ร่วมกันเก็บใน **central repository** ซึ่ง **ทุก subsystem** เข้าถึง แก้ ลบ อัปเดตได้

| Pros | Cons |
|---|---|
| แชร์ข้อมูลปริมาณมากได้มีประสิทธิภาพ | **แก้ data model ซับซ้อนและแพง** |
| แต่ละ component ทำงานอิสระ | subsystem ต้องใช้ data model ร่วมกัน มักต้องประนีประนอม |
| จัดการข้อมูลสม่ำเสมอผ่าน backup ส่วนกลาง | |

### 🔹 3) Layered Architecture
**คืออะไร:** ระบบเป็น **ชั้นซ้อนกัน** แต่ละชั้น **ขึ้นกับชั้นล่างเท่านั้น**

| Pros | Cons |
|---|---|
| **portable** ข้ามแพลตฟอร์ม | แยกชั้นให้ชัดเจนทำได้ยาก |
| แตกปัญหาซับซ้อนเป็นส่วนย่อย | **ชั้นเยอะ performance ลด** |
| **เปลี่ยนชั้นได้ถ้า interface เหมือนเดิม** | |

**ตัวอย่าง:** presentation → business logic → data access → database; OSI model

### 🔹 4) Client-Server Architecture
**คืออะไร:** แบ่งเป็น **Client** (ผู้ขอบริการ) และ **Server** (ผู้ให้บริการ)

| Pros | Cons |
|---|---|
| ใช้โครงสร้าง **distributed** ได้ | จัดการยากถ้า server อยู่ในมือบุคคลที่สาม |
| เพิ่ม/อัปเกรด server ง่าย | **server ล่มได้ถ้า request มากเกิน** |

### 🔹 5) Microservice Architecture (Martin Fowler)
- พัฒนาแอปเดียวเป็น **ชุดของ service เล็ก ๆ**
- แต่ละ service:
  - **รันใน process ของตัวเอง** สื่อสารด้วยกลไกเบา ๆ มักเป็น **HTTP resource API**
  - **deploy แยกกันได้อิสระ** ด้วยระบบ deploy อัตโนมัติ

### 🔹 6) Call and Return Architecture
**คืออะไร:** สถาปัตยกรรมที่ **ใช้มากที่สุดตั้งแต่เริ่มมีการพัฒนาซอฟต์แวร์** แตก main program เป็น component ย่อยที่เรียก component อื่นต่อได้

| Pros | Cons |
|---|---|
| จัดโค้ดเป็น module | **interface ไม่ชัดทำให้ data tight coupling** |
| scale และแก้ไขง่าย | เปลี่ยน internal data structure อาจกระทบ module อื่น |

## 3. Deriving Architectural Design: Structured Design

**Structured Design**
- **Objective:** สร้าง program architecture ที่ถูกแบ่งส่วน (partitioned)
- **Approach:** แปลง (map) **DFD** เป็น program architecture; ใช้ **PSPEC** (process specification) และ **STD** (state transition diagram) บอกเนื้อหาของแต่ละ module
- **Notation:** **structure chart**
- ผลลัพธ์คือ **Call and Return Architecture**

### 🔹 Flow Characteristics
| | ความหมาย |
|---|---|
| **Transform flow** | ข้อมูลไหลเข้า (incoming) → ถูกแปลง (transform center) → ไหลออก (outgoing) เป็นเส้นตรง |
| **Transaction flow** | ข้อมูลเข้ามาที่ **transaction center** แล้วแยกไปหลาย action path ตามชนิดของ transaction |

### 🔹 General Mapping Approach (ขั้นตอน)
1. **แยกขอบเขต incoming และ outgoing flow**; ถ้าเป็น transaction flow ให้แยก **transaction center**
2. ทำงาน **จากขอบออกไปด้านนอก** แปลง transform ใน DFD เป็น module
3. **เพิ่ม control modules** ตามต้องการ
4. **refine** โครงสร้างด้วยหลัก modularity ที่ดี
5. ทำ **"first-level factoring"**
   - ได้ **top-down distribution of control**
   - **component ชั้นบนทำการตัดสินใจ (decision-making)**, **ชั้นล่างทำงานจริงส่วนใหญ่** (input, computation, output)
   - ชั้นกลางทำ control บ้างและงานปานกลาง
6. ทำ **"second-level factoring"**

### 🔹 Factoring
- ยิ่งขึ้นไปด้านบน = **decision making เพิ่มขึ้น** ("decision making" modules)
- ด้านล่าง = **"worker" modules**

**First-level factoring:** main program controller → **input controller, processing controller, output controller**

**Second-level mapping:** แปลง transform แต่ละตัวใน DFD (A, B, C, D) เป็น module ใต้ controller โดยไล่ **จากขอบ flow ออกไป**

### 🔹 ตัวอย่าง: ระบบ Robot Control
1. **Level 1 DFD:** Operator ส่ง commands → read operator commands → determine type → analyze fixture / generate report / send control value → Robot, display screen, assembly record
2. **Level 2 DFD:** แตกละเอียด: read command, validate command, produce error msg, determine setting, format setting, read fixture status, determine type, read record, calculate output values, format report, send control value
3. **Isolate flow paths** (แยกเส้นทาง flow)
4. **Map the flow model:** `process operator commands` → `command input controller` (read command, validate command) และ `determine type` → `produce error message`, `fixture status controller`, `report generation controller`, `send control value` — แต่ละ action path ต้องขยายต่อ
5. **Refine:** ใต้แต่ละ controller เพิ่ม worker เช่น read fixture status, determine setting, format setting, read record, calculate output values, format report

## 4. Logical Module vs Physical Module

| | Logical module | Physical module |
|---|---|---|
| นิยาม | กำหนด **business activities** ที่ประกอบเป็น business process | กำหนด **กระบวนการทางกายภาพ** ที่ใช้ implement business activities |
| ตัวอย่าง (2FA) | "Two Factor Authentication" | Login → Password to First Authentication Server (external) → Password to Second Authentication Server (external) |

### 🔹 Functional Decomposition (Structure Chart)
- **Analysis:** แตก function เป็นลำดับชั้น
- **Design (physical modules) ตัวอย่าง Postal System:** Create Parcel, Bank@Post, Pay Online, Feedback, View History and Status, Update Parcel Info → แตกต่อเป็น Fill Parcel Detail, Create Tracking Number, Calculate Weight, Update Parcel History, Login, Deduct Balance ฯลฯ

```text
Create_Parcel() {
  parcelDetail = Fill_Parcel_Detail();
  trackNo = Create_Tracking_Number();
  weight = Calculate_Weight(Parcel_Detail);
  Update_Parcel_History(parcelDetail, trackNo, weight);
}
Fill_Parcel_Detail() {
  If not login_status { login(); }
  ...
  return(parcelDetail);
}
```
module ชั้นบน (Create_Parcel) **เรียก** module ชั้นล่างตามลำดับ = call and return

## 6. Software Engineering Design Principles

> 📌 **Design principles** = ข้อความที่บอกว่าอะไรทำให้ design **ดีขึ้น**

```text
Engineering Design Principles
├── Basic Principles: Feasibility · Adequacy · Economy · Changeability
└── Constructive Principles: Modularity · Implementability · Aesthetic
```

### 🔹 Basic principles
ลักษณะที่ทำให้ design ตอบความต้องการของ stakeholder ได้ดีขึ้น
| Principle | ความหมาย |
|---|---|
| **Feasibility** | design ยอมรับได้ **ก็ต่อเมื่อสร้างได้จริง** |
| **Adequacy** | ตอบความต้องการของ stakeholder ได้ **มากกว่า** (ภายใต้ข้อจำกัด) ดีกว่า |
| **Economy** | สร้างได้ **ถูกกว่า เร็วกว่า เสี่ยงน้อยกว่า** ดีกว่า |
| **Changeability** | ทำให้โปรแกรม **แก้ไขง่าย** ดีกว่า |

### 🔹 Constructive principles
จากประสบการณ์ว่าลักษณะบางอย่างทำให้ design ดีขึ้น
- **Modularity** — design ที่ดีเป็น modular
- **Implementability** — design ที่ดีสร้างง่าย
- **Aesthetic** — design ที่ดี "สวย"

## 7. Modularity

> 📌 **Modular program** = ประกอบด้วย unit ที่ **นิยามชัด เข้าใจง่าย และอิสระ** สื่อสารกันผ่าน **interface ที่นิยามชัด**

ระดับของ module: Program → sub-programs/sub-systems → packages/compilation units → classes/functions → attributes/operations/blocks → lines of code
(Software modularity: Services ⊃ Components ⊃ Objects ⊃ Modules)

**ข้อดี:** เข้าใจ/อธิบายง่าย · document ง่าย · **แก้ง่าย** · **test และ debug ง่าย** · tune ง่าย

### 🔹 Modularity Principles (5 ข้อ)
| Principle | ความหมาย |
|---|---|
| **Small modules** | module เล็กดีกว่า |
| **Information hiding** | แต่ละ module **ซ่อนรายละเอียดภายใน** (โครงสร้างและการประมวลผล) จาก module อื่น |
| **Least privilege** | module **ไม่ควรเข้าถึง resource ที่ไม่จำเป็น** |
| **Cohesion** | **"degree of relatedness"** ภายใน unit/module/object/component |
| **Coupling** | **"degree of dependence"** ระหว่าง unit/module/component |

### 🔹 Cohesion (ความเกาะกลุ่มภายใน)
- **Low cohesion:** class `Staff` มี `checkEmail()`, `sendEmail()`, `emailValidate()`, `printLetter()` — ปนหลายเรื่อง
- **High cohesion:** class `Staff` มีแค่ข้อมูลและ method ของ staff (`salary`, `email`, `setSalary`, `getSalary`, `setEmail`, `getEmail`)

**Cohesion levels — ยิ่งสูงยิ่งดี**
- สูงสุด: **Functional** — ทำ **function เดียว**
- ต่ำสุด: **Coincidental** — ทำ **หลาย function ที่ไม่เกี่ยวกัน**

### 🔹 Coupling (การพึ่งพาระหว่างกัน)
- **No dependencies** · **Loosely coupled** (พึ่งพาบ้าง) · **Highly coupled** (พึ่งพามาก)
- coupling สูง → **แก้ส่วนหนึ่งยาก** เพราะแก้ component หนึ่งกระทบทุก component ที่เชื่อมอยู่

**Coupling levels — ยิ่งต่ำยิ่งดี**
- สูงสุด (แย่สุด): **Content coupling** — เข้าถึง **ข้อมูลภายในหรือ procedural information** ของอีก module
- ต่ำสุดที่ใช้ได้จริง: **Data coupling** — ส่งแค่ **ข้อมูลที่จำเป็น**
- **No coupling** — อุดมคติแต่ไม่ practical

### 🔹 Data Coupling
- 2 component เป็น data coupled ถ้ามี **homogeneous data items**
- ทุก argument เป็น **argument ธรรมดา หรือ data structure ที่ใช้ทุก element**
- **ดีถ้าทำได้**; เขียน contract ง่ายและแก้ component แยกกันได้

| | Cohesion | Coupling |
|---|---|---|
| วัดอะไร | ความเกี่ยวข้อง **ภายใน** module | การพึ่งพา **ระหว่าง** module |
| ต้องการ | **High (Strong)** | **Low (Loose)** |
| แย่สุด | Coincidental | Content |
| ดีสุด | Functional | Data (no coupling = อุดมคติ) |

> ⭐ จำง่าย ๆ: **"High cohesion, Low coupling"** = ในห้องเดียวกันคุยเรื่องเดียวกัน, ต่างห้องคุยกันผ่านประตู (interface) เท่านั้น

### 🔹 Exercise (แนวคำตอบ)
| ข้อ | สถานการณ์ | คำตอบ |
|---|---|---|
| 1 | โมดูลเดียวทำหลายหน้าที่ (อ่านไฟล์ แสดงผล คำนวณ) | **Low cohesion** (coincidental) |
| 2 | โมดูลเรียกตัวแปรภายในของอีกโมดูลโดยตรง | **High coupling** (content coupling) |
| 3 | แต่ละโมดูลมีหน้าที่เฉพาะไม่ซ้ำซ้อน | **High cohesion** |
| 4 | โมดูลติดต่อกันผ่าน interface ที่ชัดเจน | **Low (loose) coupling** |
| 5 | แก้โมดูลหนึ่งต้องแก้โมดูลอื่นด้วย | **High (tight) coupling** |
| 6 | โมดูลเป็นเอกภาพ ทำงานเดียวให้สมบูรณ์ | **High cohesion** (functional) |

**เปรียบเทียบ design**
- **Print routine:** A รับ name, address, billing info เป็น argument · B รับ customer data structure ทั้งก้อน → A ส่งเฉพาะข้อมูลที่ใช้ = **data coupling** (coupling ต่ำกว่า) · B ส่งทั้ง structure ที่อาจมี field ไม่ได้ใช้ (แนวคำตอบ — สไลด์ไม่ได้เฉลย)
- **FileReader vs DataProcessor:** A (FileReader: open/read/close file) **cohesion สูงกว่า** · B รวมอ่านไฟล์ + คำนวณ + ส่งอีเมล = low cohesion
- **Utility vs EmployeeDatabase:** B (EmployeeDatabase เน้นเรื่องพนักงานทั้งหมด) **cohesion สูงกว่า** · A (Utility รวมทุกอย่าง) = coincidental cohesion
- สไลด์ 58 เป็นรูปภาพ อ่านเนื้อหาจากไฟล์ไม่ได้

## 8. Implementability Principles
| Principle | ความหมาย |
|---|---|
| **Simplicity** | design ที่ **เรียบง่ายกว่า** ดีกว่า |
| **Design with reuse** | design ที่ **นำของที่มีอยู่แล้วมาใช้ซ้ำ** ดีกว่า |
| **Design for reuse** | design ที่ **สร้างของที่นำไปใช้ซ้ำได้** ดีกว่า |

## 9. Aesthetic Principles
| Principle | ความหมาย |
|---|---|
| **Beauty** | เรียบง่าย ชัดเจน **ไม่ซับซ้อนเกินจำเป็น** ไม่ซ้ำซ้อน ไม่มีโครงสร้างแปลก ๆ หรือ logic ยุ่งเหยิง — **ไม่ใช่เรื่อง UI** |
| **Symmetry** | **สม่ำเสมอทั้งระบบ** component ที่คล้ายกันออกแบบคล้ายกัน |
| **Balance** | **กระจายหน้าที่และความซับซ้อน** เท่า ๆ กัน — หลีกเลี่ยง **"God classes"** (class เดียวทำทุกอย่าง) |
| **Proportion** | ขนาด component **เหมาะกับจุดประสงค์** ไม่ใหญ่เกิน (ซับซ้อน) ไม่เล็กเกิน (แตกกระจาย) |

**ตัวอย่าง Beauty:** โค้ดที่ hardcode logic, ขยายไม่ได้, อ่านยาก ❌ vs โค้ดเรียบง่าย ขยายได้ แยกหน้าที่ชัด (separation of concerns) ✓
